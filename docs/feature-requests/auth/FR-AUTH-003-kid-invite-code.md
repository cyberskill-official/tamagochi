## §1 — Description (BCP-14 normative)

§1.1  **Kids SKU has no public social sign-in.** Per FR-LEGAL-001 §1.5 + FR-AUTH-002, the kids SKU MUST NOT offer Apple / Google / Zalo Sign-In. The ONLY paths to a kids account are: (a) an invite code generated by an adult Pet+ Family-tier parent; (b) a direct parental-consent registration starting from the child's tap on "I'm under 13, my grown-up can help me."

§1.2  **Invite-code format.** Invite codes MUST be 8 characters, Crockford base32 alphabet (`0123456789ABCDEFGHJKMNPQRSTVWXYZ`, no `I/L/O/U` to avoid confusion), CSPRNG-generated, with built-in checksum (last character = sum of prior chars mod 32). Codes MUST be unique within the kids project.

§1.3  **Invite-code lifecycle.** A code MUST: (a) be generated only by a verified Family-tier parent on the standard SKU (FR-SUB-002); (b) be redeemable once; (c) expire 14 days after generation; (d) be tied to the generating parent's verified email; (e) be revocable by the parent before redemption.

§1.4  **First-launch UX (kids SKU).** On first launch the kids SKU MUST display a 3-button screen:
- "I have an invite code from my grown-up" → opens code entry;
- "My grown-up will help me sign up" → opens parental-consent registration;
- "Maybe later" → no data collection, app stays in a sandboxed try-without-account mode.

The try-without-account mode MAY persist session-scoped progress to local device storage only (no PII server-side).

§1.5  **Parental-consent registration flow.** When a child taps "My grown-up will help me sign up," the flow MUST: (a) prompt for child's display name (max 32 chars, content-safety filtered); (b) prompt for parent's email address; (c) anti-bot challenge (Cloudflare Turnstile); (d) submit to `POST /v1/auth/kids/start-consent` which: (i) creates a `parental_consent` row with `state: "pending"`; (ii) calls the chosen Safe Harbor adapter; (iii) returns a `consent_session_id` to the client.

§1.6  **Safe Harbor adapter abstraction.** A `SafeHarborAdapter` interface MUST encapsulate the vendor (PRIVO or SuperAwesome kWS) chosen per FR-LEGAL-001 §1.6. The runtime vendor is read from `process.env.SAFE_HARBOR_VENDOR ∈ {"privo", "superawesome_kws"}`. Switching vendors MUST be a runtime-config change, not a code change.

§1.7  **PRIVO flow.** When `SAFE_HARBOR_VENDOR=privo`, the adapter MUST: (a) call PRIVO's `POST /api/consent` with the child + parent email + the consent-method choice (`email_plus_card` recommended); (b) receive a PRIVO `consent_url`; (c) emit the URL via a Resend email to the parent; (d) await PRIVO's webhook callback to `/edge-functions/safe-harbor-webhook` confirming consent granted; (e) update `parental_consent.consent_state` accordingly.

§1.8  **SuperAwesome kWS flow.** When `SAFE_HARBOR_VENDOR=superawesome_kws`, the adapter MUST: (a) call kWS's `/v1/parental-verification/start` with similar payload; (b) handle kWS's specific webhook format (per kWS's documented signature scheme); (c) update `parental_consent.consent_state` accordingly.

§1.9  **Consent state transitions.** Valid transitions on `parental_consent.consent_state`:
- `pending → granted` (Safe Harbor webhook success);
- `pending → expired` (no response within 14 days);
- `granted → revoked` (parent uses revoke URL);
- Any state cannot revert to `pending`.

The state machine MUST be enforced by a Postgres trigger that REJECTS invalid transitions with `consent.state.invalid_transition`.

§1.10  **Consent revocation.** Each parental consent record MUST carry a unique `revoke_url` (cryptographically random token, included in the parental email) accessible at `GET /v1/auth/kids/revoke/<token>`. Visiting the URL: (a) marks `consent_state: "revoked"`; (b) schedules an account-deletion job via FR-LEGAL-001's DSR-erasure flow with 30-day SLA; (c) signs the parent out from any active session.

§1.11  **Sign-in for kid accounts (post-consent).** Once `consent_state == "granted"`, the child can sign in on the kids SKU by entering: (a) their invite code OR consent-issued child code (8-char Crockford base32 generated at consent grant); (b) a memorable color/animal-themed PIN (4-element sequence drawn from a fixed grid — no numeric/keyboard input, kid-friendly). Successful match yields a Supabase session.

§1.12  **No persistent device identifiers without consent.** Before `consent_state == "granted"`, the kids SKU MUST NOT persist any device-scoped identifier server-side. A session-scoped uuid is created in-memory for the consent flow; on `granted` it's anchored to the persistent `child_id`.

§1.13  **Resend email template.** Parental-consent emails MUST be sent via Resend with a Vietnamese OR English template (locale auto-detected from the kids SKU's launch country). Templates MUST: (a) clearly state the Tamagochi-Kids identity + the child's submitted display name; (b) include the Safe Harbor vendor branding; (c) include the revoke link; (d) include the policy version + privacy policy link.

§1.14  **Bot resistance.** Cloudflare Turnstile MUST gate the `POST /v1/auth/kids/start-consent` endpoint server-side. Turnstile failures emit `auth.kids.bot.suspected` Sentry event.

§1.15  **Audit logging.** Every state transition on `parental_consent` MUST emit a `coppa.consent.transition` audit-log row (via FR-INFRA-003 §1.12). Logged columns: `child_id`, `previous_state`, `new_state`, `transition_actor` (`vendor_webhook` | `parent_revoke_url` | `system_expiry`), `evidence_url`.

§1.16  **Evidence retention.** Safe Harbor vendor evidence blobs (the screenshot / video / card-verification proof) MUST be retained in `legal/` Storage bucket with 7-year retention to match COPPA-2025 audit-trail expectations. The evidence URL MUST be stored in `parental_consent.evidence_blob_url`.

§1.17  **Re-verification on graduation.** When a child crosses age 13 (per the recorded `birth_year`), the system MUST: (a) prompt the parent for graduation approval per FR-INFRA-003 §1.13; (b) once approved, mint the graduation blob; (c) the child can then sign in on the standard SKU via Apple/Google/Zalo with their parental-approval token.

§1.18  **Throttling.** A parent's email MUST NOT receive more than 3 consent requests per 24 hours, to prevent abusive spam from another adult. A child's display-name cannot be re-submitted within 1 hour of a prior pending consent.

§1.19  **Friend-graph restriction.** The kids SKU's friend graph (FR-SOCIAL-001) MUST permit **invite-code-only** addition (no name search). The parent dashboard (FR-SUB-002) provides parental approval before any new friend is added.

§1.20  **No third-party login button references.** The kids SKU sign-in UI MUST NOT contain text or icons referring to Apple / Google / Zalo / Facebook / any third-party identity provider. Even greyed-out / disabled buttons are forbidden, as they suggest a path that doesn't exist.

## §2 — Why this design

**Why no public social sign-in for under-13.** COPPA-2025 + Apple Kids Category + Google Play Families all require **verifiable parental consent before any account-data collection**. Apple/Google/Zalo Sign-In assumes a self-asserting adult; offering them on a kids app is an implicit COPPA-2025 violation. Invite-code or parental-consent registration is the only compliant path.

**Why Crockford base32 with checksum for invite codes.** Crockford base32 strips visually-confusing characters (`I/L/O/U`), reducing kid-input errors (the most common kid-support ticket source in Webkinz Next was "I can't enter the code"). The built-in checksum catches one-character typos client-side, avoiding a server roundtrip.

**Why "Maybe later" sandboxed mode exists.** A kid who launches the app + sees a parental-email gate may bounce permanently without ever showing the app to their parent. A sandboxed try-mode lets the kid play one session, get hooked, and then show the parent. Session-scoped local-only state means no PII server-side, so no COPPA gate is required.

**Why the Safe Harbor abstraction is configurable.** PRIVO is best for US-first launches; kWS is best for UK/EU; the vendor decision is post-P0 per FR-LEGAL-001 §1.6 decision-memo. Having both adapters ready means the post-decision swap is a config change.

**Why a 4-element color/animal PIN.** Kids 5-8 cannot reliably enter alphanumeric passwords. A 4-element grid-based PIN (e.g. "red bird, blue cat, green fish, yellow rabbit") is memorable, kid-friendly, and provides ~256k-2M entropy depending on grid size — sufficient for the kids account model since invite codes are also gated.

**Why no persistent device IDs pre-consent.** COPPA-2025 redefines "personal information" to include persistent identifiers used to engage with the child. Persisting one before consent = collecting PII before consent = COPPA violation. Session-scoped uuids in memory are not "persistent" in the regulatory sense.

**Why parental email throttling at 3/24h.** Without throttling, a bad-actor adult could spam another adult's email with consent requests (harassment + potential abuse). 3/24h is permissive enough for legitimate retry but blocks automated abuse.

**Why no third-party login icon at all.** Showing a greyed-out "Sign in with Google" implies a path; kids ask their parent for help and parents tap it expecting it to work. Removing the button entirely is the only clean UX.

**Why 14-day code expiry.** Long enough to forward the email to a busy parent; short enough that an unused invite code from a leaked email is bounded.

**Why graduation requires parent approval.** Even though the kid is now over 13, the legal account ownership history is on the parent's side; transferring it without re-confirming consent would create a COPPA-erasure liability.

**Why Cloudflare Turnstile and not reCAPTCHA.** Turnstile is privacy-preserving (no Google data sharing); reCAPTCHA on the kids flow would be an additional Google data-sharing surface that COPPA-2025 would scrutinise.

## §3 — API contract & code shape

### 3.1 — Start parental consent

```typescript
// apps/api/src/auth/kids/invite-code.controller.ts
@Controller('v1/auth/kids')
export class InviteCodeController {
  constructor(
    private readonly consent: ParentalConsentService,
    private readonly invite: InviteCodeService,
    private readonly turnstile: TurnstileService,
  ) {}

  @Post('start-consent')
  async startConsent(@Body() body: {
    childDisplayName: string;
    parentEmail: string;
    turnstileToken: string;
  }) {
    await this.turnstile.assertHuman(body.turnstileToken);
    return this.consent.startNewConsentFlow({
      childDisplayName: body.childDisplayName,
      parentEmail: body.parentEmail,
    });
  }

  @Post('redeem-invite-code')
  async redeemInviteCode(@Body() body: { code: string; pin: string[] }) {
    return this.invite.redeem(body.code, body.pin);
  }

  @Get('revoke/:token')
  async revokeViaUrl(@Param('token') token: string) {
    return this.consent.revokeByToken(token);
  }
}
```

### 3.4 — Parental consent schema (kids project)

```sql
-- infra/supabase/kids/migrations/20260517_002_parental_consent.sql
create table parental_consent (
  id uuid primary key default gen_random_uuid(),
  child_id uuid references auth.users(id),
  child_display_name text not null,
  parent_email_hash text not null,
  parent_email_encrypted bytea,                  -- pgcrypto
  consent_state text not null
    check (consent_state in ('pending','granted','revoked','expired')),
  consent_method text not null
    check (consent_method in ('email_plus_card','knowledge_based','government_id')),
  vendor text not null check (vendor in ('privo','superawesome_kws')),
  vendor_request_id text not null,
  evidence_blob_url text,
  revoke_token text not null unique,
  granted_at timestamptz,
  expires_at timestamptz,
  revoked_at timestamptz,
  policy_version text not null,
  created_at timestamptz not null default now()
);

-- State transition enforcement
create or replace function enforce_consent_transition() returns trigger as $$
begin
  if old.consent_state = 'granted' and new.consent_state = 'pending' then
    raise exception 'consent.state.invalid_transition (granted→pending)';
  end if;
  if old.consent_state = 'revoked' and new.consent_state != 'revoked' then
    raise exception 'consent.state.invalid_transition (revoked→%)', new.consent_state;
  end if;
  return new;
end; $$ language plpgsql;

create trigger trg_consent_transition before update on parental_consent
  for each row execute procedure enforce_consent_transition();
```

// apps/api/src/auth/kids/__tests__/parental-consent.spec.ts
import { describe, it, expect, beforeAll } from 'vitest';
import { ParentalConsentService } from '../parental-consent.service';
import { fakeSafeHarbor } from './_helpers/fake-safe-harbor';

describe('FR-AUTH-003 — parental consent', () => {
  let svc: ParentalConsentService;
  beforeAll(() => { svc = new ParentalConsentService(fakeSafeHarbor('superawesome_kws')); });

  it('starts pending; webhook flips to granted', async () => {
    const { consent_session_id } = await svc.startNewConsentFlow({
      childDisplayName: 'Mochi-Fan', parentEmail: 'parent@example.com',
    });
    let row = await svc.byId(consent_session_id);
    expect(row.consent_state).toBe('pending');

    await fakeSafeHarbor('superawesome_kws').simulateGrant(consent_session_id);
    row = await svc.byId(consent_session_id);
    expect(row.consent_state).toBe('granted');
  });

  it('rejects state regression granted→pending', async () => {
    const { consent_session_id } = await fakeSafeHarbor('superawesome_kws').granted();

      .rejects.toThrow(/consent.state.invalid_transition/);

      await svc.startNewConsentFlow({ childDisplayName: `c${i}`, parentEmail: 'a@b.c' });
    }
    await expect(svc.startNewConsentFlow({ childDisplayName: 'c4', parentEmail: 'a@b.c' }))
      .rejects.toThrow(/throttled/);
  });
});

## §6 — Implementation skeleton

```typescript
// apps/api/src/auth/kids/parental-consent.service.ts
@Injectable()
export class ParentalConsentService {
  constructor(
    private readonly vendor: SafeHarborAdapter,
    private readonly supa: SupabaseClient,
    private readonly throttle: ParentalEmailThrottle,
    private readonly mailer: ResendMailer,
    private readonly turnstile: TurnstileService,
  ) {}

  async startNewConsentFlow(input: { childDisplayName: string; parentEmail: string }) {
    await this.throttle.assertWithinLimit(input.parentEmail);
    const childId   = await this.createPendingChildRow(input);
    const revokeTok = randomBytes(32).toString('hex');
    const { consentUrl, vendorRequestId } = await this.vendor.startVerification({
      childId, parentEmail: input.parentEmail, childDisplayName: input.childDisplayName, locale: 'vi',
    });
    await this.supa.from('parental_consent').insert({
      child_id: childId,
      child_display_name: input.childDisplayName,
      parent_email_hash: sha256(input.parentEmail),
      consent_state: 'pending',
      vendor: process.env.SAFE_HARBOR_VENDOR,
      vendor_request_id: vendorRequestId,
      revoke_token: revokeTok,
      expires_at: new Date(Date.now() + 14 * 24 * 3600 * 1000).toISOString(),
      policy_version: await this.policyVersion(),
    });
    await this.mailer.sendParentalConsentEmail({ to: input.parentEmail, consentUrl, revokeUrl: revokeTok });
    return { consent_session_id: childId };
  }
}
```
